What changed since the capability refactor

Three things are new. Events gained a hierarchy — NewPlatformMessage is now the base, with IncomingMessagePlatformEvent and OutgoingMessagePlatformEvent extending it. A preprocessing stage runs before routing, so participants and chats exist in the database before any pipeline needs them. And the persona's own replies come back as events: TelegramMessageCapability pushes each sent message onto a messageSubject, the runtime turns that into an OutgoingMessagePlatformEvent, and it re-enters the same loop — so both sides of a conversation land in history through one code path.

The loop

  1. Emit. TelegramRuntime produces IncomingMessagePlatformEvent from the gramJS listener and OutgoingMessagePlatformEvent from its own capability's subject. Both carry a ConversationRef holding the native handle plus platform-neutral meta.sender / meta.chat.
  2. Preprocess. EventHandlerPreprocessor upserts the ParticipantEntity and ChatEntity from conversation.meta. It is awaited before routing, so the pipelines can assume both rows exist.
  3. Route (fan-out). PlatformEventHandlerService tests instanceof twice, and because IncomingMessagePlatformEvent extends NewPlatformMessage an incoming message matches both: it is persisted by NewMessagePipeline and reacted to by IncomingMessagePipeline. An outgoing message matches only the first.
  4. Decide. IncomingMessageReactionPlanner builds the vocabulary, converts each Zod schema with z.toJSONSchema(), assembles the prompt from composable templates, and asks Gemini for an ordered IPlan[].
  5. Act. PlaneResolverService rebuilds the same vocabulary, matches by name, and calls execute(). Sending a message emits an outgoing event, closing the circle back at step 1.

What's working well

  • One vocabulary, two sources — platform capabilities vary by runtime, app capabilities are always present, and both the planner and the resolver derive the union rather than declaring it.
  • The persistence model is properly normalized — unique indexes on (platform, platformChatId), (platform, platformUserId) and (chat, platformMessageId) mean redelivery is idempotent, and messages defaults to ORDER BY createdAt ASC so history reads in order.
  • Prompt assembly is composable — Prompt.use(template) with PlannerPromptTemplate / PersonaInformationTemplate / BasicRulesTemplate moves prompt text out of the planner, so wording can change without touching planning logic.
  • Preprocessing removed a whole class of ordering bug — the write-then-read dependency between participant creation and message insertion is now explicit and sequenced.

Known gaps — marked on the diagram

  • 1AppDelayCapability.execute() is still empty. The body is {}, so the persona never pauses — the one capability whose whole purpose is pacing does nothing.
  • 2ReadMessageCapability.execute() is a concrete no-op rather than abstract. Telegram overrides it; a future platform that forgets gets silent success.
  • 3The plan is never validated. Zod schemas only generate the prompt's JSON Schema — nothing calls .parse() on the reply, and JSON.parse(response.text || '') throws on an empty response.
  • 4Unknown names are silently skipped — capability?.execute(...) produces no error and no log for a hallucinated name.
  • 5Bootstrap floats its promises. contexts.map(async …) is never awaited, so a bad session or a missing platform.sender becomes an unhandled rejection and you get no report of which personas actually started.
  • 6mergeMap gives no ordering. Events for the same conversation run concurrently, so a typing indicator and a reply can interleave across chats. groupBy(conversationKey) + concatMap would serialize per conversation while keeping different conversations parallel. Pipeline results are also discarded with void, so errors inside them vanish.
  • 7Lookups ignore the platform column. findParticipantByPlatformId and findChatByPlatformChatId filter on the id alone, while the unique indexes are composite — correct for Telegram-only, wrong the moment a second platform lands.
  • 8synchronize: true still auto-alters the schema on boot. Now that there are real message rows worth keeping, this is the moment to switch to migrations.

Two structural leaks worth noting as well: ConversationRef imports EntityLike from telegram/define and core/platform/types.ts aliases IPlatformSender = TelegramSender, so core still names Telegram directly; and impl/telegram/types.ts imports ChatType from a database entity, pointing the platform layer at persistence. Root cause of 3 and 4 remains Capability<T = unknown, S = unknown> — unconstrained generics leave the resolver's dispatch site with no type safety at all.
