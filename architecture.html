entity-core — Architecture

NestJS · per-account runtimes · closed perceive→decide→act loop · Gemini planner · capability-only vocabulary · Telegram

core / orchestration platform impl inbound (perceive) ai (decide) outbound (act) capabilities — the vocabulary entities persistence known gap

The action layer is gone. Previously an Action carried the model-facing schema and a resolve() that did nothing but delegate to a capability — two parallel lists that had to be kept in sync by hand. Now a capability is the whole unit: it declares its own name, description, and Zod schema, and it executes itself. There is exactly one list, so nothing can drift out of sync.

The loop

  1. Perceive (green). TelegramRuntime emits an IncomingMessagePlatformEvent on its RxJS $events subject. RuntimeOrchestrator subscribes and forwards to PlatformEventHandlerService, which routes by instanceof to IncomingMessagePipeline.
  2. Decide (purple). SendMessagePlannerService builds the vocabulary — the runtime's capabilities plus the app registry's — converts each Zod schema with z.toJSONSchema(), and hands Gemini an anyOf array as the response schema. The model returns an ordered IPlan[].
  3. Act (orange). PlaneResolverService rebuilds the same vocabulary, matches each plan item by name, and calls execute(). The Telegram capability holds the client and performs the real I/O — that's the outbound arrow back into the runtime.

Why this shape works

  • One vocabulary, two sources. Platform capabilities come from the connected runtime and therefore vary by platform; app capabilities come from a DI singleton and are always available. The planner and the resolver derive the union rather than declaring it, so the model can never be offered something the runtime can't do.
  • The execute(args, input) split. args is injected by the runtime (the ConversationRef); input is what the model filled in against the schema. That boundary is what the old action's resolve() was doing by hand.
  • Contract vs. implementation. The abstract capability owns the model-facing contract — name, prompt text, schema — while the Telegram subclass owns only the SDK call. A second platform is one file per capability, and the model's vocabulary stays identical across platforms.
  • Adding an ability is now: enum entry, abstract contract, one impl per supporting platform. The runtime's wiring is untouched — ReadMessageCapability was added exactly this way.

Known gaps — marked on the diagram

  • 1AppDelayCapability.execute() is empty. The body is {}, so the persona never actually pauses. DelayAction used to call delay(ms) — this is a regression from the refactor.
  • 2ReadMessageCapability.execute() is a concrete no-op rather than abstract. Telegram overrides it, but any future platform that forgets gets silent success.
  • 3The plan is never validated. Zod schemas are used only to generate the prompt's JSON Schema; nothing calls .parse() on Gemini's reply. JSON.parse(response.text || '') also throws on an empty response.
  • 4Unknown names are silently skipped. capability?.execute(...) — a hallucinated name produces no error and no log. The conversation guard the old actions had is also gone, so a missing conversation is a TypeError instead of a clear failure.

Root cause of 3 and 4 is the same: Capability<T = unknown, S = unknown> leaves both generics unconstrained, so the resolver's dispatch site has no type safety at all. Constraining S extends ZodType and parsing the plan with a z.discriminatedUnion('name', …) closes both.
